## 1. 项目概述

### 1.1 项目背景

- 成员为**大二软件学院**学生，已掌握 **Java**，完成过 **Java 版俄罗斯方块**。
- 每人每日可用学习时间约 **1.5 小时**，两人时间**不一定完全同步**。
- 采用**双人组队**方式开发，目标是产出一份**可写入简历的完整项目**。

### 1.2 项目目标

- 产出一个可运行、可写入简历的完整后端业务项目。
- 务实优先，**不追求超大项目**，兼顾以下能力训练：
  - Git 团队协作
  - 需求拆分
  - 接口对齐
  - 代码评审
  - 分工开发

### 1.3 项目范围与边界

- **做**：后端接口为主，覆盖用户、图书、借阅三大业务模块。
- **不做**：复杂前端页面；前端用简单 HTML / Postman 调试即可，避免前端工作量爆炸。
- **裁剪原则**：优先保证核心业务跑通，非核心功能（如图书分类、分页高级筛选）可后置。

### 1.4 技术栈选型

| 类别 | 选型 | 说明 |
| --- | --- | --- |
| 语言 | Java | 已掌握 |
| 框架 | SpringBoot | 后端主框架 |
| 数据库 | MySQL | 关系型存储 |
| ORM | MyBatis-Plus | 简化 CRUD |
| 权限 | Sa-Token | 登录鉴权与角色权限 |
| 工具 | Lombok | 减少样板代码 |
| 缓存（可选） | Redis | 热门图书缓存，第 9 周引入 |

### 1.5 协作约束

- 每天每人 **1.5 小时**，严格控制，**课内优先，不熬夜**。
- 两人时间不一定同步，按**各自分支 + 定期同步**方式推进。
- 训练重点：**Git 团队协作、需求拆分、接口对齐、代码评审、分工开发**，而不是单纯各写各的代码。

## 2. 核心协作原则

1. **同一个项目，不各写一套**：统一仓库、统一数据库、统一接口文档。
2. **分工明确**：按模块拆分；不简单"一人前端一人后端"，后端内部也拆分业务模块。
3. **必须使用 Git**：分支、PR、合并、冲突解决——这是企业真实工作流程，也是面试加分点。
4. **核心优先**：优先保证核心业务跑通，非核心功能可裁剪，不追求大而全。
5. **节奏可控**：课内优先，不熬夜，1.5 小时严格控制。

## 4. 前期准备（第 0 周，1–2 天，两人一起完成）

### 4.1 Git 仓库与分支规范

1. 创建 GitHub 仓库，两人都加入协作者。
2. 约定分支规范：
   - `main`：稳定可运行版本
   - `dev`：开发主分支
   - `feature-xxx`：每个人自己的功能分支

### 4.2 协作规则

- **先对齐接口文档**：开发前用 Markdown 写简单接口文档，约定入参、出参、状态码。
- **先 pull 再提交**：提交前先 pull，解决冲突。
- **小步提交 PR**：完成一个小功能，提交 PR 到 `dev`，互相做简单 code review。
- **定期同步**：每周至少一次 15–20 分钟简短同步，对齐进度、解决卡点。

### 4.3 分工初步划分

> 分工可在后期调整。

**方案：后端双人**

| 成员 | 负责模块 |
| --- | --- |
| A 同学 | 用户权限模块（登录、注册、token、角色权限）、全局异常、统一返回封装 |
| B 同学 | 业务核心模块（图书 CRUD、借阅、归还、借阅记录） |

### 4.4 数据库表协作约定

- 数据库表由**两人一起设计**，不允许一个人私自改表结构。
- 表结构变更必须**同步给对方**。

## 5. 阶段一：基础能力对齐（第 1–3 周）

**阶段目标**：两人补齐 SpringBoot、MySQL、MyBatis-Plus 基础；搭建统一项目骨架，完成基础 demo。

> 每人每日 1.5 小时。

### 5.1 第 1 周：SpringBoot + Maven 环境对齐

- **学习内容**：SpringBoot 基础注解、Maven 依赖、接口开发；Git 团队协作实操（分支、pull、push、解决简单冲突）。

**任务清单**：

| 序号 | 任务 |
| --- | --- |
| 1 | 两人各自熟悉项目仓库，完成本地环境搭建 |
| 2 | 共同搭建项目骨架，统一 pom.xml 依赖 |
| 3 | 各自写一个简单测试接口，提交 PR 合并到 dev 分支，练习协作流程 |

**产出**：共享仓库，项目骨架搭建完成，两人都能跑通项目。

### 5.2 第 2 周：MySQL + MyBatis-Plus

- 共同完成数据库设计：用户表、图书表、借阅记录表；画 ER 图，写建表 SQL。
- 两人分别练习 Mapper、实体类编写。
- 练习：各自写简单 CRUD 接口，提交合并。

**重点**：表结构改动必须两人同步，不要私自修改。

### 5.3 第 3 周：小练习 —— 改造俄罗斯方块（Web 版，可选）

- 可选练习，不强制，**不作为主项目**，仅用来熟悉协作。
- 后端提供分数提交、排行榜接口。
- 可一人负责接口，一人负责简单页面调用。

### 5.4 阶段验收

- 两人都熟悉 SpringBoot + MySQL。
- 掌握 Git 团队开发流程。
- 主项目骨架完成。

## 6. 阶段二：核心业务开发（第 4–8 周）

**阶段说明**：主项目为图书管理系统，按前期分工推进，每周同步进度。这是**双人核心开发期**。

### 6.1 第 4 周：需求梳理、接口文档、骨架完善

1. 两人一起梳理需求：
   - **用户**：注册、登录、角色区分（普通用户、管理员）
   - **图书**：图书新增、查询、修改、删除
   - **借阅**：借书、还书、借阅记录查询
2. 编写接口文档，约定所有接口的请求方式、参数、返回格式。
3. 完善项目基础配置：统一返回结果、全局异常处理器。

**分工**：A 同学负责权限模块基础；B 同学搭建图书业务基础结构。

### 6.2 第 5 周：各自模块开发

| 成员 | 任务 |
| --- | --- |
| A 同学 | 实现用户注册、登录，Sa-Token 鉴权，角色权限校验 |
| B 同学 | 图书基础 CRUD 接口，借阅、归还基础业务逻辑 |

**注意**：调用对方模块接口先看接口文档；需要改动接口必须两人沟通。每天写完自己的功能提交 PR，互相简单看代码。

### 6.3 第 6 周：业务逻辑完善 + 边界条件处理

| 成员 | 任务 |
| --- | --- |
| A 同学 | 完善权限控制：普通用户只能看自己借阅记录，管理员可管理全部图书 |
| B 同学 | 处理业务边界：图书已借出不能再次借阅；归还时间校验；借阅记录生成 |

> 遇到 bug，两人互相协助排查，不要一个人硬扛。

### 6.4 第 7 周：参数校验、日志、完善接口

- 统一增加 `@Valid` 参数校验。
- 引入日志 logback。
- 完善全部接口，使用 Postman 做接口测试。
- 两人一起测试整套流程：**注册 → 登录 → 借书 → 还书 → 查询记录**，跑通完整业务链路。

### 6.5 第 8 周：项目初步收尾，修复 bug

1. 两人一起回归测试，修复发现的 bug。
2. 合并 `dev` 分支到 `main` 分支。
3. 编写 README，记录项目简介、技术栈、数据库表说明、启动方式。

### 6.6 阶段产出

- 双人协作完成完整可运行的业务后端项目。
- GitHub 仓库完整提交记录，可写进简历。

> **现实提醒**：进度慢时，优先保证核心流程跑通；次要功能（图书分类、分页高级筛选等）可后置。

## 7. 阶段三：项目优化与工程化（第 9–10 周）

**阶段说明**：不新开项目，基于现有图书管理系统做优化，依然双人协作。

### 7.1 第 9 周：Redis 缓存 + 环境配置

- 分工：一人负责引入 Redis，实现热门图书缓存；另一人负责区分开发/生产配置文件。
- 一起讨论缓存带来的问题：缓存与数据库一致性，简单思考方案（不一定全部实现）。

### 7.2 第 10 周：单元测试 + 部署学习（可选）

1. 各自给自己负责的模块写简单 JUnit 单元测试。
2. 学习 Docker 打包部署（时间不够可跳过）。
3. 共同整理踩坑笔记：遇到的 bug、Git 冲突、接口对齐问题，记录下来。

**重点**：学会工程化思维，不只是把功能跑通。

## 8. 阶段四：项目复盘与面试素材（第 11–12 周）

**阶段说明**：不再大量写新代码，重点把双人项目变成面试素材。两人一起复盘，每人独立整理自己的面试素材。

### 8.1 第 11 周：项目深度复盘

两人一起讨论：

1. 项目整体架构、模块划分。
2. 团队协作中遇到的问题：Git 冲突、接口不一致、需求理解偏差如何解决。
3. 业务问题：并发借阅会出现什么问题？如何优化？缓存击穿如何处理？

> 不需要全部代码实现，**思考 + 写笔记**即可。

### 8.2 第 12 周：简历素材整理

1. 分别整理简历项目描述：写清楚自己负责的模块、技术点、遇到的难点与解决方案。
2. 整理 GitHub 仓库：完善文档，整理提交记录。
3. 有余力可加一个小 demo；没时间就到此为止。

> **重点**：双人项目面试时，一定要讲清楚**自己做了哪一部分、和同学如何协作**，不要写成"我们做了一个项目"。

## 9. 风险预案

| 序号 | 风险 | 应对措施 |
| --- | --- | --- |
| 1 | 两人时间不同步 | 不要等对方，各自在自己分支开发；每周固定 15–20 分钟同步 |

| 4 | 出现 Git 冲突 | 不直接覆盖，两人一起协商解决 |
| 5 | 一人包办 / 一人划水 | 分工落到具体模块，每人都有独立代码贡献 |

## 附录 B：数据库表设计（参考）

> **说明**：以下为参考设计，用于起步和统一思路；**最终表结构以两人共同设计为准**，任何变更须同步对方。

### B.1 ER 关系

- 用户 `user`（1）——（N）借阅记录 `borrow_record`（N）——（1）副本 `book_copy`（N）——（1）图书 `book`（N）——（M）类型 `book_type`。
- 用户 `user`（1）——（N）通告 `announcement`
- 一本书可有多个分类，一个分类下有多本书，经中间表 `book_type_rel` 关联。
- 借阅记录通过 `user_id`、`book_copy_id` 关联用户与副本。

### B.2 用户表 `user`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | 主键，自增 | 用户 ID |
| username | VARCHAR(50) | 唯一，非空 | 用户名 |
| password | VARCHAR(100) | 非空 | 密码（加密存储） |
| role | TINYINT | 非空，默认 0 | 角色：0=普通用户，1=管理员 |
| status | TINYINT | 非空，默认 1 | 账号状态：1=正常，0=禁用 |
| create_time | DATETIME | 非空 | 创建时间 |
| update_time | DATETIME | 非空 | 更新时间 |

### B.3 图书表 `book`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | 主键，自增 | 图书 ID |
| isbn | VARCHAR(20) | 唯一 | ISBN 号 |
| title | VARCHAR(100) | 非空 | 书名 |
| author | VARCHAR(50) | — | 作者 |
| publisher | VARCHAR(100) | — | 出版社 |
| create_time | DATETIME | 非空 | 创建时间 |
| update_time | DATETIME | 非空 | 更新时间 |

### B.4 借阅记录表 `borrow_record`

| 字段           | 类型 | 约束 | 说明                  |
|--------------| --- | --- |---------------------|
| id           | BIGINT | 主键，自增 | 记录 ID               |

| book_copy_id | BIGINT | 非空，索引 | 关联副本 ID             |

| due_time     | DATETIME | 非空 | 应还时间                |
| return_time  | DATETIME | 可空 | 实际归还时间（NULL=未还）     |

### B.5 类型表 `book_type`

| 字段   | 类型 | 约束 | 说明 |
|------|  | --- | --- |
| id   | BIGINT | 主键，自增 | 类型 ID |

### B.6 类型关联表 `book_type_rel`

| 字段      | 类型 | 约束 | 说明 |

| book_id | BIGINT | 非空，索引，主键 | 关联图书 ID |

### B.7 副本表 `book_copy`

|-------------|  | --- |---------|

### B.9 建表 SQL（参考）

```sql

CREATE TABLE `user` (
`id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '用户ID',
`username` VARCHAR(50) NOT NULL COMMENT '用户名',
`password` VARCHAR(100) NOT NULL COMMENT '密码（加密存储）',
`role` TINYINT NOT NULL DEFAULT 0 COMMENT '角色：0=普通用户，1=管理员',
`status` TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1=正常，0=禁用',
`create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
`update_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
PRIMARY KEY (`id`),
UNIQUE KEY `uk_username` (`username`)
)ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT '用户表';
```

## 附录 C：接口文档模板

> 每个接口开发前按此模板对齐，写在 Markdown 文件中。

```markdown
### 接口名称：用户登录

- **URL**：`POST /api/user/login`
- **请求头**：`Content-Type: application/json`

**请求参数**：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| username | String | 是 | 用户名 |
| password | String | 是 | 密码 |

- **请求示例**：`{"username":"alice","password":"123456"}`

**响应参数**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | Integer | 状态码，200 表示成功 |
| message | String | 提示信息 |
| data | Object | 返回数据（token 等） |

- **响应示例**：`{"code":0,"message":"ok","data":{"token":"xxxx"}}`
```

**通用约定**：

- 统一返回结构：`{ code, message, data }`。
- 状态码约定：`0` 成功；`4xx` 客户端错误；`5xx` 服务端错误（可自定义业务错误码）。
- 鉴权接口在请求头携带 `token`。

## 附录 D：Git 协作命令清单

### D.1 常用命令

| 命令 | 说明 |
| --- | --- |
| `git clone <url>` | 克隆仓库 |
| `git checkout -b feature-xxx` | 新建并切换功能分支 |
| `git add .` | 暂存改动 |
| `git commit -m "描述"` | 提交 |
| `git pull origin dev` | 拉取 dev 最新代码 |
| `git push origin feature-xxx` | 推送功能分支 |
| `git merge dev` | 合并 dev 到当前分支 |

### D.2 标准协作流程

1. `git checkout dev && git pull origin dev` —— 同步最新 dev。
2. `git checkout -b feature-xxx` —— 新建功能分支。
3. 开发、`git add`、`git commit`。
4. `git push origin feature-xxx`，在 GitHub 发起 PR 到 `dev`。
5. 对方 review 后合并，删除功能分支。

### D.3 冲突处理

1. 冲突时先 `git pull` 拉取对方代码。
2. 打开冲突文件，两人一起协商保留哪部分。
3. 解决后 `git add` 冲突文件并 `git commit`。
